# CORRECTIONS.md — history of where this repo and the spec diverged

`CLAUDE.md` says: "When this repo and the spec disagree, the spec wins — unless you believe the
spec is wrong, in which case stop and say so." This file is where "said so" got recorded during
Phases 1–3. Each finding has since been folded directly into `docs/BASE-DESIGN.md`,
`docs/APP-DESIGN.md`, or `docs/INTEGRATION-GUIDE.md` — those three are the single source of
truth from Phase 4 onward, not this file.

What's kept here is the **history**: a one-line pointer to where each correction landed and
what the original error was. Several of these are traps that will recur when the app-package
template gets built (the `banned-api`/factories subpath problem in particular), so the record
stays even though the docs no longer need it to be correct.

## Applied (Phases 1–4)

1. **Pre-commit mypy hook is `repo: local`, not a pinned mirror** — `docs/APP-DESIGN.md` §3.6, `docs/BASE-DESIGN.md` §5.1. Original spec text showed mypy as a pinned-`rev` mirror hook; a mirror's isolated venv can't satisfy `strict = true` + `mypy_django_plugin` + a `django_settings_module`, which needs the whole project importable.
2. **The `*.factories` rule is a grep hook, not a `banned-api` ruff entry** — `docs/BASE-DESIGN.md` §5.2. Spec asked for a `*.factories` entry in the `banned-api` table; `per-file-ignores` disables a rule *code* per path, and `core/**` must already ignore `TID251`, so a factories entry would be silently disabled exactly where it needs to catch violations — not expressible in ruff, enforced by grep instead.
3. **Security settings block (`SECURE_*`/cookie/HSTS)** — `docs/BASE-DESIGN.md` §4.3 (settings excerpt) and §7 (CI env). §4.3's shown code block omitted this block entirely, and without it `manage.py check --deploy --fail-level WARNING` (§7's CI job) fails against an otherwise-unset settings module.
4. **`jazzmin` precedes `django.contrib.admin` in `INSTALLED_APPS`** — `docs/BASE-DESIGN.md` §4.3. Spec's excerpt listed `django.contrib.admin` first; jazzmin overrides admin templates via the *first* matching app in `INSTALLED_APPS`, so the original ordering silently unthemes the admin with nothing to catch it.
5. **Request-ID `ContextVar`/middleware/filter live in `config/logging.py`** — `docs/BASE-DESIGN.md` §3. Spec required request-ID correlation but named no file for the plumbing and didn't list a `middleware.py` in §2's tree; co-located in `config/logging.py` instead, alongside `build_logging_config()`, since all three exist only to serve it.
6. **WebSocket composition point** — `docs/BASE-DESIGN.md` §3, "WebSockets" subsection. Not a wrong statement to correct, a gap: the spec never said how `config/asgi.py`'s `ProtocolTypeRouter` composition works, who owns it, or the `get_asgi_application()`-before-any-consumer-import ordering requirement.
7. **Realtime as an app package's fourth public surface** — `docs/APP-DESIGN.md` §6, "Realtime (optional fourth surface)" subsection. Same category as #6: the two-surface rule (`signals.py`/`services.py`) never addressed what a package exposes for a WebSocket consumer.
8. **The ephemeral test stack (`docker-compose.test.yml`) and a minimal `Makefile` pulled forward to Phase 3** — landed in the repo (`Makefile`, `docker-compose.test.yml`), not in one of the three design docs; their *content* (`docs/BASE-DESIGN.md` §5.3, §10.2) was already correct. `docs/CLAUDE-CODE-GUIDE-BASE.md`'s phase breakdown put these in Phases 5/8, leaving no phase before 8 with a tracked way to run the tests Phase 3 writes. **Not folded into the guide — it wasn't one of the three docs named for this pass; flagged as a decision, not silently applied.**
9. **`config/tests/` scoped into Phase 3, not left for later** — same shape as #8: a phase-sequencing fact, not a content error in `docs/BASE-DESIGN.md` §5.4 or `docs/INTEGRATION-GUIDE.md` §4 (both already correctly describe *what* to test). `backend/pyproject.toml`'s `--cov=config --cov-fail-under=80` makes this load-bearing regardless of which phase the guide assigns it to. **Same flag as #8.**
10. **The `tools/mixins.py` error envelope, previously unspecified** — `docs/BASE-DESIGN.md` §3 (envelope shape + `code` list) and `docs/APP-DESIGN.md` §4 (cross-reference). Spec described `tools/mixins.py` in one line ("shared DRF mixins/error formats") with no concrete shape for `APP-DESIGN.md` §4's "same shape" to point at.
11. **`docker-compose.test.yml`/`Makefile` `test` target gaps** — `docs/BASE-DESIGN.md` §5.3 and §10.2 (both code blocks). `test-redis` had no healthcheck, so `up -d --wait` didn't actually wait for it; the `test` target set only `POSTGRES_HOST`/`POSTGRES_PORT`, leaving the suite on `backend/.env`'s dev credentials and `redis://redis:6379/0` — neither reachable from the test containers.
12. **Bug, not a spec deviation: `RequestIDMiddleware` broke every real request** — `docs/BASE-DESIGN.md` §3 (logging bullet). A Phase 2 implementation bug, not a place the spec was wrong: the middleware never called `markcoroutinefunction(self)`, so `SecurityMiddleware` (wrapping it) couldn't detect it as async and called it without awaiting — confirmed to 500 every request through the real ASGI app, not just the test client. Found and fixed in Phase 3; regression-tested in `backend/config/tests/test_asgi_integration.py`.
15. **The SDK-to-host frontend client contract was unspecified, and the one code example touching it was self-contradictory** — `docs/APP-DESIGN.md` §12 (new "SDK-to-host client contract" and "When provider nesting gets unwieldy" subsections, updated manager/hook examples, updated §2 folder tree, updated §8 README usage example), `docs/INTEGRATION-GUIDE.md` §2 (new provider-mount step, install step 10; removal steps updated to match), §4 (composition example annotated), `docs/CLAUDE-CODE-GUIDE-APP.md` Phase 5 (file list and review criteria updated). §12 said an SDK's base URL "comes from the host's shared client configuration," but its own manager example did `import { apiClient } from "./client"` as though the SDK owned a client module — the SDK can't import the host's `frontend/lib/api-client.ts` (project-owned, not part of a publishable package) and the host isn't a publishable package either, so neither direction of that import can exist. Resolved as runtime dependency injection via React context: each SDK declares a structurally-typed `HttpClient` interface matching `frontend/lib/api-client.ts`'s actual `ApiClient` shape (`get`/`post`/`patch`/`delete`), ships a `<XProvider client basePath>` + internal `useXConfig()` in `api/context.tsx` (replacing the old `api/client.ts`), and the manager becomes instance-based — constructed per-hook via `useMemo` from the injected client, never a static class. `basePath` is a provider prop (defaulting to the app's suggested prefix) because `INTEGRATION-GUIDE.md` §3 already said the mount path is the host's choice, which the old hardcoded manager paths (`apiClient.get("/")`) never honored. Doc-only correction — no code changed, since no app package exists yet to hold the code this describes.

## Applied (Phase 5)

16. **`.gitignore`** (no BASE-DESIGN.md section — not a spec code block) — unanchored `lib/` silently excluded `frontend/lib/` from git; builds only worked because the files sat on disk.
17. **`docs/BASE-DESIGN.md` §8.1** (dev `backend/Dockerfile` block) — the block contradicted its own `.venv`-gotcha prose; never set `UV_PROJECT_ENVIRONMENT`, so the bind mount shadowed the container's venv.
18. **`docs/BASE-DESIGN.md` §8.1** (prod `backend/Dockerfile.prod` `CMD`) — hardcoded `--workers 3` against its own "derive from CPU count" notes bullet; uvicorn reads `$UVICORN_WORKERS` natively, so the flag is gone and compose sets the env var instead.
19. **`docs/BASE-DESIGN.md` §4.2 and §8.1** — `uv sync --no-dev` only excludes the `dev` group, not `test` (`[tool.uv] default-groups = ["dev","test"]`); the prod builder needed `--no-default-groups`, and would have shipped `pytest`/`factory-boy`/etc. into production otherwise.
20. **`docs/BASE-DESIGN.md` §8.2** (`celery-beat` command) — the healthcheck polled a pidfile the command never wrote; celery beat's own default is no pidfile at all. Added `--pidfile=/tmp/celerybeat.pid`.
21. **`docs/BASE-DESIGN.md` §8.2 and §3** — spec named `mailhog`, unmaintained since 2020; replaced with pinned `axllent/mailpit`.
22. **`docs/BASE-DESIGN.md` §3** (new email bullet) — `config/settings.py` had no `EMAIL_*` settings at all, so nothing pointed at mailhog or mailpit; added them plus `config.E004`.
23. **`docs/BASE-DESIGN.md` §8.1 and `CLAUDE.md`'s pinned-versions table** — the `uv` image pin (`0.9`) trailed the toolchain that writes `backend/uv.lock` (`0.11.19`) by two minors, and the table never listed `uv` or `Redis` at all.
24. **`docs/BASE-DESIGN.md` §8.2** (frontend healthcheck fragment) — `http://localhost:3000/...` is permanently unreachable on `node:22-alpine` (musl resolves `localhost` to `::1` first; BusyBox `wget` doesn't fall back to IPv4). Verified empirically. Changed to `127.0.0.1`.
25. **`docs/BASE-DESIGN.md` §8.2** (backend healthcheck) — needed a real decision, not a mechanical edit; see "Needed a decision" below. Final shape: prod healthcheck sends `-H "X-Forwarded-Proto: https"` rather than exempting `/healthz/` from `SECURE_SSL_REDIRECT` at the settings level; `ALLOWED_HOSTS` guidance now requires `127.0.0.1`.
26. **`docs/CLAUDE-CODE-GUIDE-BASE.md` Phase 9** — verification had no fresh-clone step; #16 above would have been caught immediately by one. Added a `git clone`-based check ahead of the final "follow README" step.
27. **`docs/CLAUDE-CODE-GUIDE-BASE.md` Phases 5 and 8** — the guide assigned the entire `Makefile` to Phase 8, but its compose-dependent targets are unblocked as soon as `docker-compose.yml` exists (Phase 5). Split accordingly; `lint`/`fmt`/`typecheck`/`check`/`deploy` remain Phase 8.
28. **`docs/BASE-DESIGN.md` §8.2 and §9, `backend/config/views.py`** — `/healthz/` (unauthenticated by design) returned the raw `str(exc)` from a failed DB/cache check, which names the internal hostname (confirmed empirically: `"failed to resolve host 'db': ..."`, `"...connecting to redis:6379..."`). Masked to a generic `"unavailable"` string when `DEBUG` is off, matching `tools/mixins.py`'s existing DEBUG-gated exception-detail pattern; real detail still logged server-side. Added a §9 note that nginx must not proxy `/healthz/` to the public internet regardless.

### Needed a decision, not a mechanical edit

Two Phase 5 findings weren't simple "match the prose" fixes — recorded here so they aren't mistaken for routine edits:

- **#25** — the initial fix (Phase 5 draft) exempted `/healthz/` from `SECURE_SSL_REDIRECT` via `SECURE_REDIRECT_EXEMPT`, which works but makes the endpoint reachable over plaintext wherever the path is proxied. Replaced with a healthcheck-side `X-Forwarded-Proto: https` header, which uses the trust path (`TRUST_PROXY_SSL_HEADER`) the app already has instead of adding a new exemption. No settings-level bypass remains; plain HTTP to `/healthz/` still redirects like every other path.
- **#28** — surfaced only because #25 prompted a closer look at what `/healthz/` actually returns on failure; not something the original defect list anticipated. The masking behavior (real detail in dev, generic in prod) is a design choice, not a bug fix with one obvious answer — flagged in case a future project wants the opposite trade-off (e.g., an internal-only healthcheck endpoint that's fine leaking detail).

## Applied (Phase 6)

29. **`docs/BASE-DESIGN.md` §7** (`backend-tests` env) — `SECRET_KEY: ci-only-not-a-secret` is 20 characters and trips `security.W009` (needs ≥50 chars, non-`django-insecure-`-prefixed); `check --deploy --fail-level WARNING` exited 1. Verified empirically against a `git archive` export with no local `.env` (the true CI condition). Replaced with a `Generate ephemeral CI keys` step that writes a `secrets.token_urlsafe(64)` value to `$GITHUB_ENV` at runtime, rather than a longer literal — see #31.
30. **`docs/BASE-DESIGN.md` §7** (`backend-tests` env) — the job set no `EMAIL_BACKEND`; `config/settings.py` defaults it to the SMTP backend with `EMAIL_HOST=mailpit`, which trips `config.E004` as an **ERROR** (not a warning) once `DEBUG=False`. Verified in the same run as #29 — fixed together, both blocked `check --deploy` on the first push. Set `EMAIL_BACKEND=django.core.mail.backends.locmem.EmailBackend`, which is also the correct backend for a test run regardless of the check.
31. **`docs/BASE-DESIGN.md` §7** (`backend-tests` env) — `FERNET_KEY: ${{ secrets.CI_FERNET_KEY }}` requires a GitHub secret configured per clone and is withheld from fork PRs, so a fork's CI never goes green. Replaced with the same runtime-generation step as #29 (`base64.urlsafe_b64encode(os.urandom(32))`, stdlib only, no `cryptography` import needed) — verified the generated value round-trips through `Fernet.encrypt`/`.decrypt`. This makes the workflow require zero configured GitHub secrets; stated as an explicit rule in the workflow's header comment, with the one expected future exception (a private-repo app-package token, `APP-DESIGN.md` §1.2) named alongside it.
32. **`docs/BASE-DESIGN.md` §7** — `PYTHON_VERSION: "3.14"` was declared at workflow level and never referenced anywhere in the file; `security-audit`'s `setup-node` hardcoded `node-version: "22"` instead of using the declared `NODE_VERSION`. Dropped `PYTHON_VERSION` (`.python-version` is the single source of truth and `setup-uv` already reads it — a second declaration is a second place to drift) and wired `security-audit` to `${{ env.NODE_VERSION }}`.
33. **`docs/BASE-DESIGN.md` §7** (`frontend` job) — ran `ruff format --check` on the backend but no formatting check on the frontend, so `prettier` was enforced only by pre-commit, which is opt-in per clone and therefore not a real CI gate. Added `npm run format:check` (script already existed in `frontend/package.json`; verified `npx prettier --check .` passes on the current tree).
34. **`docs/BASE-DESIGN.md` §7** (`security-audit`) and **`docs/APP-DESIGN.md`** (app-package CI template, same job) — both used `uv export --no-dev`, the identical defect CORRECTIONS #19 already found and fixed in the prod Docker builder: `--no-dev` is only an alias for `--no-group dev` and leaves the `test` group in the exported/audited set. Verified empirically: `--no-dev` exports 6 test-group packages (`pytest`, `factory-boy`, `freezegun`, …), `--no-default-groups` exports 0. Fixed both call sites to `--no-default-groups`, added `--locked` (fail loudly on a stale lock rather than silently audit a stale dependency set) and `--no-deps` on the `pip-audit` side (the export is already fully resolved with hashes, so re-resolving is redundant).
35. **`docs/BASE-DESIGN.md` §4.1** (prose, line 238) — "keep test/lint tooling out of production images with a single `--no-dev` flag" directly contradicted §4.2's own correction three sections later (`--no-dev` alone is insufficient; `--no-default-groups` is required). Same root cause as #19 and #34 — three live sites of one defect, found by `git grep -- '--no-dev'` across the whole repo rather than by reading §7 in isolation. Corrected the prose to name `--no-default-groups` with a forward reference to §4.2.
36. **`docs/BASE-DESIGN.md` §7** (`docker-build`) — no mention of `--ssh`, though `backend/Dockerfile.prod` mounts `--mount=type=ssh` on its `uv sync` layers for private app-package refs (`APP-DESIGN.md` §1.2). Not a failure today — BuildKit treats an unconnected `type=ssh` mount as optional by default — but nothing said what changes once a project installs its first private app package. Added a comment on the job naming the concrete addition (`webfactory/ssh-agent` step, `--ssh default` on the buildx call) and a matching note in `docs/INTEGRATION-GUIDE.md` §2 at the point someone actually hits it (installing the backend half of a private-repo app).

### Needed a decision, not a mechanical edit (Phase 6)

- **#29/#31** — the alternative considered was widening `--fail-level` or hardcoding a longer literal key/secret directly in the workflow file. Rejected: a literal, however long, is still a value that sits in the repo and gets copied forward into every project cloned from this scaffold, eventually into a real `.env`. Runtime generation with the system `python3` (no dependency on the project's own venv existing yet) has no such failure mode and costs one extra step.
